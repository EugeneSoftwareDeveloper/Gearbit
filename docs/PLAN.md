# Gearbit — план реализации

> Рабочее название: **Gearbit**. Это программа для Windows, через которую ребёнок за ПК (большой монитор, клавиатура, мышь, геймпад) управляет роботом-конструктором и программирует его на **Scratch**, **Python** и **C#**.
> Первый робот — **Apitor / Makerzoid SuperBot** (контроллер TUDAO). Архитектура сразу рассчитана на другие похожие роботы.

Сопутствующие документы:
- [ARCHITECTURE.md](ARCHITECTURE.md) — диаграммы компонентов, языки и технологии, путь команды до робота;
- [PROTOCOL-SUPERBOT.md](PROTOCOL-SUPERBOT.md) — что известно о протоколе;
- [STAGE0-CHECKLIST.md](STAGE0-CHECKLIST.md) — замеры на роботе;
- [devices/tudao-superbot.json](../devices/tudao-superbot.json), [profiles/superbot-car.json](../profiles/superbot-car.json) — описание робота и сборки (пока с заглушками, `verified: false`).

## 1. Цели и принципы

| Цель | Как достигаем |
|---|---|
| Удобно заниматься с ребёнком за ПК | Окно на весь экран, крупные элементы, русский язык, клавиатура и геймпад, большая кнопка СТОП |
| Три уровня программирования | Переключатель **Пульт · Scratch · Python · C#**, один и тот же API во всех языках |
| Разные роботы | Робот описан **набором возможностей** (моторы, датчики, свет…), а не конкретным классом. Протокол и транспорт подключаются как адаптеры |
| Безопасность | СТОП с любого экрана, watchdog, ограничение скорости, остановка при обрыве связи и при завершении программы |
| Приватность | Всё локально, без облака, аккаунтов и телеметрии. Никаких сторонних SDK |
| Можно без робота | Симулятор — такой же «робот», как настоящий |

**Нецели первой версии:** мобильные платформы, облачное хранение, многопользовательская работа через интернет.

## 2. Архитектура

### 2.1. Главная идея: один «хаб» владеет роботом, клиентов много

По BLE к роботу подключается **только хаб** (локальный .NET-сервис). Все остальные (пульт, Scratch, программы на Python и C#) работают с хабом через **один API** (JSON-RPC поверх WebSocket на `localhost`).

Так устроены Scratch Link у LEGO и micro:bit, а также многие промышленные системы. Что это даёт:
- одна точка, где живут безопасность (СТОП, watchdog, лимиты) и логирование;
- клиенты не знают ни про BLE, ни про байты, только «мотор», «датчик», «свет»;
- новый язык программирования добавляется как ещё один тонкий клиент;
- пользовательские программы можно запускать **в отдельном процессе** и при необходимости просто убить его.

```
┌──────────────────────────── Gearbit (окно WPF + WebView2) ─────────────────────────────┐
│  [Пульт]   [Scratch]   [Python]   [C#]          Робот ▾   Сборка ▾   🔋   ● Подключён  [СТОП] │
│                                                                                           │
│   UI (HTML/TS): пульт, редактор Monaco, встроенный Scratch (TurboWarp), телеметрия, консоль │
└───────────────┬───────────────────────────────────────────────────────────────────────────┘
                │ JSON-RPC / WebSocket  ws://localhost:PORT
┌───────────────▼───────────────────── Gearbit.Hub (ASP.NET Core) ────────────────────────┐
│ RobotManager ─ ControlArbiter ─ SafetySupervisor (СТОП, watchdog, лимиты) ─ Telemetry bus │
│ ProgramRunner: запускает Python/C# в отдельных процессах, СТОП = kill + motors off       │
└───────────────┬───────────────────────────────────────────────────────────────────────────┘
                │ IRobot (возможности)
┌───────────────▼──────────── Драйверы (адаптеры) ────────────────────────────────────────────┐
│ RobotDriver = DeviceDescriptor + IProtocol + ITransport                                    │
│   Протоколы: TudaoUart (FF FE…FD FC) │ ApitorF0FF (55 AA…) │ Simulator │ позже: micro:bit…  │
│   Транспорты: WinRT BLE │ Loopback (симулятор/тесты) │ позже: Serial/USB, TCP (ESP32)      │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
       ▲                         ▲                              ▲
 Python-скрипт            C#-скрипт / NuGet              Scratch-расширение
 (пакет `gearbit`)     (`Gearbit.Client`)           (JS, тот же WebSocket)
```

### 2.2. Модель робота: возможности, а не классы

Роботы различаются количеством моторов и датчиков, прошивкой и способом подключения. Поэтому **нет** классов вроде `SuperBot : Robot`. Робот — это контейнер компонентов (composition over inheritance, похоже на компоненты в ROS и на hub/ports в LEGO SPIKE).

```csharp
public interface IRobot : IAsyncDisposable
{
    RobotInfo Info { get; }                       // модель, прошивка, батарея, транспорт
    IReadOnlyList<IRobotComponent> Components { get; }
    T Get<T>(string id) where T : IRobotComponent; // robot.Get<IDistanceSensor>("front")
    IEnumerable<T> All<T>() where T : IRobotComponent;
    ConnectionState State { get; }
    IObservable<TelemetryFrame> Telemetry { get; }
    Task StopAllAsync(CancellationToken ct = default);
}

// Возможности (каждая — маленький интерфейс)
public interface IMotor          : IRobotComponent { Task SetPowerAsync(int percent); }   // -100..100
public interface IDistanceSensor : IRobotComponent { DistanceReading Current { get; } }   // raw + level + см (если откалибровано)
public interface IImu            : IRobotComponent { Tilt Current { get; } }              // наклон X/Y, ускорение
public interface ILight          : IRobotComponent { Task SetColorAsync(RobotColor c); }
public interface ILineSensor     : IRobotComponent { bool OnLine { get; } }   // у SuperBot сделано проще: тот же IDistanceSensor глазом вниз + LineLevel
public interface IBattery        : IRobotComponent { int? Percent { get; } bool Low { get; } }
// позже: IServo, ISpeaker, IColorSensor, IButton, ICompass ...
```

Над физическими компонентами есть **сборка** (build profile): что из чего собрано. Контроллер один, а собрать из него можно машинку, кран или динозавра.

```jsonc
// profiles/superbot-car.json — «Машинка»
{
  "id": "superbot-car",
  "title": "Машинка",
  "robot": "tudao-superbot",
  "drive": { "type": "differential", "left": "M1", "right": "M2", "invertRight": true },
  "aliases": { "front": "D1", "right": "D2" },         // куда смотрят датчики в этой сборке
  "limits": { "maxPower": 60 },                         // детский режим
  "calibration": { "D1": { "levels": [0, 3, 6, 10, 15, 20, 30] } } // уровень → см (заполняется мастером калибровки)
}
```

Отсюда «высокоуровневые» возможности: `IDifferentialDrive.Drive(left, right)`, `Turn(...)`. Это **декоратор** поверх двух `IMotor`, который учитывает инверсию и лимиты.

### 2.3. Адаптеры: дескриптор + протокол + транспорт

| Абстракция | За что отвечает | Реализации v1 | Позже |
|---|---|---|---|
| `ITransport` | Передать и получить байты, состояние соединения | `WinRtBleTransport` (Nordic UART / любой GATT), `LoopbackTransport` | `SerialTransport`, `TcpTransport` (ESP32 Wi-Fi), `WebBluetoothTransport` (Blazor WASM) |
| `IRobotProtocol` | Кодировать команды и разбирать уведомления. **Чистые функции, без I/O** | `TudaoUartProtocol` | `ApitorF0FFProtocol` (Robot J и др.), `MicroBitProtocol` |
| `DeviceDescriptor` (JSON) | Как найти устройство (префиксы имени, UUID сервисов), какие компоненты у него есть, какую версию прошивки ожидать | `tudao-superbot.json` | По одному файлу на модель |
| `IRobotDriverFactory` | `Probe(advertisement) → совпадение / уверенность`, затем `CreateAsync()` | `TudaoDriverFactory`, `SimulatorDriverFactory` | Плагины из отдельных сборок |

Паттерны: **Adapter** (протокол и транспорт), **Strategy** (протокол выбирается по дескриптору), **Factory + Registry** (поиск драйверов через DI, `services.AddRobotDriver<TFactory>()`), **Decorator** (лимиты, инверсия, логирование трафика), **Observer** (телеметрия через `IObservable`/`IAsyncEnumerable`), **State machine** (соединение).

Пример дескриптора:

```jsonc
// devices/tudao-superbot.json
{
  "id": "tudao-superbot",
  "title": "Apitor / Makerzoid SuperBot",
  "match": { "namePrefixes": ["Nordic_TUDAO", "Apitor"], "services": ["6e400001-b5a3-f393-e0a9-e50e24dcca9e"] },
  "transport": { "type": "ble-gatt", "write": "6e400002-…", "notify": "6e400003-…", "mtu": 20 },
  "protocol": "tudao-uart",
  "components": [
    { "id": "M1", "type": "motor" }, { "id": "M2", "type": "motor" }, { "id": "M3", "type": "motor" },
    { "id": "D1", "type": "distance", "range": [0, 6] }, { "id": "D2", "type": "distance", "range": [0, 6] },
    { "id": "IMU", "type": "imu", "firmware": ">=v2" },
    { "id": "L1", "type": "light" }, { "id": "L2", "type": "light" }, { "id": "L3", "type": "light" }, { "id": "L4", "type": "light" },
    { "id": "BAT", "type": "battery" }
  ]
}
```

Компоненты, которые зависят от прошивки (например, гироскоп только в 19-байтовых кадрах), драйвер включает **после** первого кадра телеметрии. UI и Scratch показывают только реально доступные блоки и индикаторы.

**Составной робот** (на будущее, но модель это уже допускает): логический робот = SuperBot (моторы) + micro:bit или ESP32 (компас, лазерный дальномер). Это одна сборка, в которой компоненты собраны из двух устройств.

### 2.4. Особенности SuperBot, которые учитывает драйвер

- Протокол **основан на состоянии**: каждый раз отправляется полный 14-байтовый кадр (все моторы и свет). Поэтому драйвер хранит **желаемое состояние**, и вызовы `SetPower` только меняют его. Отдельный цикл отправляет кадр **при изменении, но не чаще N Гц**: последняя запись побеждает, BLE не забивается очередью.
- Скорость внутри API всегда в процентах −100..100. В байты устройства её переводит протокол. Диапазон проверяем на этапе 0.
- Датчики приходят сами, в уведомлениях. Драйвер различает 11- и 19-байтовые кадры (старая и новая прошивка).

### 2.5. Хаб: API (JSON-RPC 2.0 через WebSocket)

```
robots.scan()                         → [{id, name, model, rssi}]
robots.connect({id}) / disconnect()
robot.info()                          → модель, прошивка, компоненты, сборка
control.acquire({client, priority})   → lease (кто сейчас «за рулём»)
motor.set({id, power})                ; drive.set({left, right}) ; drive.stop()
light.set({id, color})
sensor.read({id})                     → значение (обычно не нужно: есть подписка)
emergency.stop()                      → всегда работает, без lease
program.run({lang, source}) / program.stop()
── уведомления сервера ──
telemetry   {t, distance:{front, right}, imu:{x, y, acc}, battery, motors:{…}}   ~20 Гц
connection  {state, reason}
program     {state, stdout, stderr, error:{line, message}}
log         {dir:"tx"|"rx", hex}      (режим разработчика)
```

**ControlArbiter.** Моторами в каждый момент управляет один клиент: пульт **или** программа. Когда запускается программа, пульт переходит в режим «только смотреть», кроме кнопки СТОП. Аварийная остановка работает всегда, вне очереди.

**SafetySupervisor:**
- **Watchdog (deadman)**: клиент с lease шлёт heartbeat. Нет связи больше 500 мс — моторы стоп.
- Обрыв BLE, конец или падение программы, закрытие окна — моторы стоп.
- Ограничение мощности из сборки (детский режим) и плавный разгон, без рывков из 0 в 100.
- Низкий заряд — предупреждение в UI.
- Горячие клавиши СТОП: **Пробел / Esc** на любом экране, кнопка «B» на геймпаде.

### 2.6. Запуск программ

| Язык | Где редактируется | Как запускается | СТОП |
|---|---|---|---|
| Блоки (Scratch) | Вкладка «Блоки»: scratch-blocks (редактор) | Свой интерпретатор в интерфейсе, клиент хаба с `source:"program"` | «Стоп» на панели + общий СТОП; уход с вкладки — стоп |
| Python | Monaco в Gearbit **или** любой внешний редактор (VS Code, IDLE) | Отдельный процесс: встроенный portable Python + пакет `gearbit` | Kill процесса + motors off |
| C# | CodeMirror в Gearbit **или** Visual Studio / Polyglot Notebooks | Отдельный процесс `Gearbit.ScriptHost` (Roslyn Scripting), глобальная переменная `robot` | Kill процесса + motors off |

Пользовательский код работает в отдельном процессе, потому что бесконечный цикл `while(true){}` в .NET нельзя прервать внутри процесса. Kill процесса надёжен всегда.

### 2.7. Единый API для ребёнка во всех языках

Одинаковые понятия и имена, разный синтаксис. Ниже одна и та же программа «Исследователь».

**Scratch** (блоки на русском):
```
когда нажат флаг
повторять всегда
  если <(расстояние [впереди]) < (2)> то
    ехать [влево] мощность (40)
    ждать (0.4) секунд
  иначе
    если <(расстояние [справа]) < (2)> то
      ехать левым (30) правым (50)
    иначе
      ехать [вперёд] мощность (50)
```

**Python:**
```python
from gearbit import robot, wait

while True:
    if robot.distance("front") < 2:
        robot.turn_left(40)
        wait(0.4)
    elif robot.distance("right") < 2:
        robot.drive(30, 50)
    else:
        robot.forward(50)
```

**C#:**
```csharp
while (true)
{
    if (robot.Distance("front") < 2)
    {
        robot.TurnLeft(40);
        Wait(0.4);
    }
    else if (robot.Distance("right") < 2)
        robot.Drive(30, 50);
    else
        robot.Forward(50);
}
```

Состав API v1: `forward/backward/turn_left/turn_right/drive(l, r)/stop`, `motor(id).power(p)`, `distance(id)`, `tilt()`, `battery()`, `light(id).color(c)`, `wait(s)`, события `on_distance(id, below=…)`, `on_tilt(dir)`.
Для взрослых: `robot.raw.send(bytes)` и подписка на сырые кадры (режим разработчика).

### 3.1. Режимы

- **Пульт**: WASD или стрелки, геймпад (Gamepad API), отдельные кнопки ▲/▼ для каждого мотора, ползунок скорости, выбор цвета фар, большие индикаторы датчиков. «Умный тормоз» включается галочкой: это пример того, что программа может работать вместе с ручным управлением.
- **Scratch**: встроенный редактор с категорией «Робот». Справа та же панель датчиков.
- **Python / C#**: редактор кода (CodeMirror) с подсветкой, автодополнением API робота (по stub-файлам), подсветкой строки с ошибкой и консолью. Кнопки ▶ и ■.
- **«Посмотреть как код»** (этап 6): из Scratch-проекта генерируется Python или C#, сначала только для чтения. Мостик от блоков к тексту, как в MakeCode и LEGO SPIKE.

### 3.2. Сквозные элементы

- Большая **кнопка СТОП** справа сверху, всегда видна, Пробел/Esc.
- Индикатор связи и батареи. При обрыве — понятное сообщение и автопереподключение.
- **Переключатель «Симулятор»**: тот же интерфейс, робот виртуальный.
- **Детский / взрослый режим**: во взрослом видны лог байтов, сырые кадры, настройки сборки и калибровки.
- **Мастер калибровки датчиков**: «поставь коробку на 5 см → нажми» → таблица уровень → см в сборке.
- **Задания** (этап 6): карточки «Умный тормоз», «Исследователь», «Лабиринт», «Робот-пёс» с подсказками и шаблонами на трёх языках.
- Проекты хранятся обычными файлами в `Документы\Gearbit\` (`.sb3`, `.py`, `.cs`) с автосохранением.

## 4. Технологии

| Слой | Выбор | Почему |
|---|---|---|
| Платформа | **.NET 10 (LTS)**, `net10.0-windows10.0.19041.0` для BLE | Основной язык — C#, LTS |
| BLE | WinRT `Windows.Devices.Bluetooth` (GattSession, MaintainConnection) | Нативно в Windows 10/11, без драйверов. Спаривать робота не нужно |
| Хаб | ASP.NET Core (Kestrel, только `localhost`), StreamJsonRpc или свой тонкий JSON-RPC | Один процесс, WebSocket из коробки |
| Оболочка | WPF + **WebView2** | Окно на весь экран. UI можно открыть и в обычном браузере |
| UI | TypeScript + Vite без фреймворка, CodeMirror 6 | Лёгкий фронтенд. Сначала планировался Monaco, выбран CodeMirror: меньше и проще красится темами |
| Блоки | **scratch-blocks** (Apache-2.0, Blockly 12) + свой интерпретатор | Без GPL и без Scratch VM, общая тема с интерфейсом. Сначала планировался TurboWarp scratch-gui, см. [docs/dev/blocks.md](dev/blocks.md) |
| C#-скрипты | Roslyn Scripting (`Microsoft.CodeAnalysis.CSharp.Scripting`) в процессе `ScriptHost`, лежит в папке `csharp` рядом с хабом | Компиляция на лету, понятные ошибки с номерами строк, ничего не нужно ставить |
| Python | Python 3.9+ с компьютера (позже — встроенный portable) + пакет `gearbit` на стандартной библиотеке | Пакет работает и из внешних IDE |
| Тесты | xUnit + «золотые» кадры из реальных захватов, Playwright для UI | Протокол — чистые функции, тестировать легко |
| Установка | Один каталог или MSIX, позже — автообновление | — |

## 7. Лучшие практики, которые закладываем сразу

1. **Hardware Abstraction Layer + возможности.** Код программ не знает модель робота. (ROS, LEGO SPIKE, Open Roberta)
2. **Один владелец соединения, много клиентов.** (Scratch Link)
3. **Безопасность в хабе, а не в клиентах:** СТОП, watchdog, лимиты, остановка при любых сбоях.
4. **Протокол — чистые функции**, тестируются золотыми кадрами из реальных захватов. Транспорт отдельно.
5. **Состояние вместо потока команд:** желаемое состояние + цикл отправки с ограничением частоты.
6. **Дескрипторы устройств и сборки в JSON**: новый робот или новая сборка часто не требуют кода.
7. **Определение прошивки по данным** (длина кадра) и включение компонентов по факту.
8. **Пользовательский код в отдельном процессе**, СТОП всегда срабатывает.
9. **Симулятор как полноценный драйвер**: обучение без железа, автотесты без железа.
10. **Режим разработчика**: hex-лог, ручная отправка кадров, запись и воспроизведение телеметрии. Это помогает разбирать новые роботы.
11. **Одинаковый API во всех языках** и путь роста: Scratch → «посмотреть как код» → Python/C#.
12. **Детский UX**: крупно, по-русски, понятные ошибки («Робот не подключён — включи его и нажми „Найти“»), автосохранение.
13. **Приватность**: всё офлайн, никаких аккаунтов, аналитики и сторонних SDK.

## 9. Риски и открытые вопросы

| Вопрос | Как закрываем |
|---|---|
| Диапазон скорости и реакция на частоту кадров не подтверждены | Этап 0, захваты |
| 2 или 4 мотора, какие порты | Этап 0. Сборка описывает маппинг, код не меняется |
| Разные прошивки (11/19 байт), возможно другой ключ авторизации | Определение по данным, ключ в дескрипторе |
| Капризы WinRT BLE (кэш GATT, переподключение) | `BluetoothCacheMode.Uncached`, `GattSession.MaintainConnection`, понятные ошибки |
| Задержка BLE при реакции на датчики | Средние скорости в автономных режимах, частота отправки 20–30 Гц. Измерить на этапе 0 |
| Лицензии: scratch-gui (BSD-3), TurboWarp (GPL-3.0), BlocosLab (AGPL-3.0) | Выбран scratch-blocks (Apache-2.0): GPL-зависимостей нет |
| Протокол неофициальный, прошивка может обновиться | Не обновлять прошивку из официального приложения без нужды. Дескрипторы версионируются |
